# Recoto 通報対応ランブック

最終更新: 2026-09-05
運営者: HERAC LLC
公開窓口: `herac.7.app@gmail.com`

## 前提

- `content_reports` はクライアントから読めない。通報者情報は対象者に開示しない。
- 通報確認は Supabase Dashboard の承認済み運用アカウント、または同等の service-role バックエンドだけで行う。service-role key はアプリ、ブラウザ、チケット本文に入れない。
- コンテンツの通常閲覧は避け、該当通報の `content_snapshot` と関連IDのみを確認する。
- 自動フィルターだけで利用停止を確定せず、文脈とコミュニティガイドラインに基づき人が判断する。

## 毎日のキュー確認

1. `status in ('received', 'reviewing')` を、`created_at` の古い順に確認する。
2. 確認を始めた通報を `reviewing` にする。通常は2営業日以内に一次判断する。
3. 切迫した身体危険、具体的脅迫、児童の性的搾取の疑いは最優先で同日中にエスカレートする。違法性の判断が必要な場合は専門家または適切な機関に相談する。
4. 判断と理由を最小限の運用記録に残し、`actioned` または `dismissed` と `resolved_at` を同時に更新する。
5. 通報者への個別回答が必要な場合は公開窓口のみを使い、対象者に通報者を推測できる情報を送らない。

## 判断と対応

- 問題なし、風刺、引用、誤認: `dismissed`
- 単発の軽微な違反: 該当共有行を非公開または削除し、`actioned`
- 嫌がらせ、差別、性的搾取、詐欺、個人情報曝露、反復違反: 該当共有行を削除。必要に応じて対象をグループから除名し `group_bans` を作成。対応後 `actioned`
- 生命への具体的脅迫や児童の性的搾取: 閲覧・複製を最小限にし、関連IDとタイムスタンプを保全。即時にエスカレートし、利用可能性を停止する。

グループ所有者はアプリ内の「除名して再参加を防ぐ」を使える。運営者が対応する場合は、承認済みの service-role 操作で、同一トランザクション内にて次の順序を守る。

1. `group_bans` を作成する。
2. 対象の `shared_entries` を削除する。
3. 対象の `group_members` を削除する。
4. 通報の `status` と `resolved_at` を更新する。

## 異議申し立て

- `herac.7.app@gmail.com` で受け付け、対象グループ、発生日時、申し立て内容を確認する。
- 最初の判断者以外が再確認できる場合は分離する。
- 通報者情報は異議申し立て側に開示しない。
- 復旧が妥当な場合はコンテンツまたは参加資格を復旧し、運用記録に理由を残す。

## 保持と定期削除

- 通報と最小限の証拠は不正対応のため180日保持する。それ以上の保持に法的必要性がある場合は、別のアクセス制御済み記録に根拠と期限を残す。
- service role から `purge_expired_content_reports()` を毎日1回実行する。一回の上限は500件のため、0件が返るまで再実行する。
- 本番公開前に定期実行の成功ログと、180日を超えた通報が残っていないことを確認する。

## 本番公開前チェック

- コミュニティガイドラインとサポートページの URL が本番 HTTPS で開く。
- アプリから通報し、キューに `received` と証拠スナップショットが入る。
- 通報者・対象者のどちらも通報テーブルを読めない。
- ブロック後すぐと再起動後の両方で、相手の共有内容が表示されない。
- 所有者が除名したユーザーは、同じ招待コードで再参加できない。
- ゲストから Google/Apple アカウントへ引き継いだ後も、ブロック、通報、除名履歴が保たれる。
